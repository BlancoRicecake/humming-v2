## 2. 데이터 계약 (`public.app_announcements`)

| 열 | 내용 |
|---|---|
| `id` | `^[a-z0-9][a-z0-9_-]{0,63}$`, 기본 키 |
| `revision` | 1 이상. 내용(종류, 제목, 본문, 버튼)이 바뀌면 **trigger가 자동으로 1 올린다**. 운영자가 직접 올리면 그 값을 그대로 둔다. 낮추면 거부된다. 게시 여부, 기간, 대상만 바꿀 때는 그대로다. 새 revision은 새 공지로 취급한다(읽음·확인 다시) |
| `kind` | `info`(소식) / `important`(중요) / `critical`(긴급) |
| `title_ko`, `title_en` | 1~120자 |
| `body_ko`, `body_en` | 1~4000자, 일반 텍스트(HTML·스크립트 해석 없음) |
| `published` | 기본값 **false**(초안). 앱에는 true인 행만 보인다 |
| `starts_at`, `ends_at` | timestamptz(UTC로 저장). `ends_at`은 비워 둘 수 있고, 있으면 `starts_at`보다 뒤여야 한다 |
| `platforms` | `android`, `ios`, `windows`, `macos`의 1개 이상 부분집합 |
| `min_build`, `max_build` | 선택. 앱 빌드 번호(`pubspec`의 `+43` 부분) 범위이며 경계값을 포함한다 |
| `action_label_ko`, `action_label_en`, `action_url` | 선택. 세 개 모두 있거나 모두 비어야 한다. URL은 `https://(*.)hum-track.com/…`, `https://apps.apple.com/…`, `https://play.google.com/…`, `mailto:humtrack@gmail.com`만 허용 |

- **RLS:** anon과 authenticated는 `published and starts_at <= now() and (ends_at is null or ends_at > now())`인 행만 SELECT할 수 있다. 쓰기와 trigger 함수 호출은 막혀 있다. 운영자는 대시보드(소유자 권한)에서 관리한다.
- **앱의 읽기 요청:** `GET {SUPABASE_URL}/rest/v1/app_announcements?select=…&order=starts_at.desc&limit=50`. 헤더는 `apikey`와 `Authorization`에 **공개 anon key**만 넣는다. 사용자 토큰도, 엔진 API도 거치지 않는다. 그래서 분석·클라우드 서버가 내려가 있어도 공지를 읽는다.
- **기기 쪽 재검증:** 같은 규칙을 앱에서도 다시 검사한다. 잘못된 행 하나는 건너뛰고 나머지는 표시한다. 허용되지 않은 링크는 버튼만 빼고 공지는 표시한다.
- **기기 쪽 제한:** 최대 50개, 응답 256KB. 이를 넘거나 목록 형태가 아닌 응답은 "실패"로 보고 기존 캐시를 유지한다.

## 3. 앱 동작

- **시작:** 로컬 캐시만 읽고 곧바로 돌아온다. 네트워크 요청은 백그라운드에서 연결 5초, 수신 8초, 전체 12초 제한으로 보낸다. 동시에 들어온 갱신 요청은 하나로 합친다. 앱이 다시 활성화되면 갱신하되 15분에 한 번까지만 한다. SUPABASE 설정이 없는 로컬 빌드에서는 기능이 조용히 꺼진다.
- **캐시와 상태 파일** (`looptap/announcements/feed.json`, `state.json`)
  - 앱 저장소에 원자적으로 쓴다. 한 번에 하나씩, 쓰기마다 고유한 임시 파일, Windows rename 거부 시 재시도, 원본을 먼저 지우지 않음.
  - 실패·손상·과대 응답은 아무것도 바꾸지 않는다.
  - 성공한 빈 응답은 **회수**로 반영한다(캐시도 비운다).
  - 캐시 파일이 손상돼도 앱은 빈 상태로 시작한다.
- **오래된 캐시** (마지막 성공 후 7일 넘게 오프라인): 공지 센터에만 "인터넷에 연결되지 않아 {날짜}에 받은 공지" 안내와 함께 보여 주고, 배너와 팝업에는 쓰지 않는다. 종료 시각이 지난 공지는 네트워크 없이도 바로 사라진다.
- **홈 배너:** 읽지 않은 공지 중 가장 중요한 것 하나(긴급 > 중요 > 소식, 같으면 최신)와 "모두 보기(N)"를 보여 준다. 모두 읽었으면 작은 "공지사항 N" 링크만 남는다. 일반·중요 공지는 팝업을 띄우지 않는다.
- **긴급 팝업:**
  - 곡 목록이 맨 위 화면이고(시트, 대화상자, 편집기 등 다른 화면이 위에 없음) 앱이 활성 상태일 때만 띄운다. 그래서 편집·재생·카운트인·녹음 중에는 뜨지 않는다. 그동안 받은 공지는 홈으로 돌아왔을 때 보여 준다.
  - 같은 실행에서는 id@revision마다 한 번만 띄운다.
  - "확인"을 누르면 이 기기에 저장되고, 같은 revision은 다시 뜨지 않는다.
  - "나중에"는 읽음으로만 처리한다. 확인이 아니므로 다음 실행 때 다시 뜬다.
  - 긴급 공지도 공지 센터에서 다시 열 수 있다.
- **공지 센터와 상세 화면:** 읽은 공지도 계속 목록에 남는다. 상세 화면은 스크롤되고 텍스트를 선택할 수 있다. 링크 버튼은 사용자가 누를 때만 외부 앱으로 연다. 긴급 공지를 아직 확인하지 않았으면 상세 화면에 "확인" 버튼이 있다.
- **기존 동작:** 재생, 저장, 모달 흐름은 바꾸지 않았다. 홈 화면에 배너 위젯 하나를 추가했을 뿐이다.

## 4. 검증

| 앱 공지 UI | 10 통과 |

| Windows RELEASE 빌드 | 성공 (`mobile/build`) |

SQL 테스트가 확인한 항목:
- anon과 authenticated에게는 게시됐고 활성인 행만 보인다. 초안, 예약, 종료 공지는 조건을 걸어 조회해도 보이지 않는다.
- 클라이언트의 INSERT, UPDATE, DELETE와 trigger 함수 호출이 거부된다.
- revision은 내용이 바뀔 때만 자동으로 오르고, 게시·기간·대상 변경에는 유지되며, 명시적으로 올린 값은 존중하고, 낮추면 거부한다.
- 잘못된 종류, id, 빈 제목, 과대 본문, 역전된 기간, 허용되지 않은 플랫폼, 빈 플랫폼, 빌드 범위 역전, http·외부 도메인·file 링크, 라벨 없는 링크는 거부된다. 정상 링크와 대상 지정은 허용된다.
- 마이그레이션을 다시 실행해도 문제가 없다.

앱 테스트가 확인한 항목:
- 계약 재검증(잘못된 행 건너뜀, 중복 id, 50개 제한)과 링크 허용 목록. `file`, `intent`, `javascript`, 다른 메일, 포트나 사용자 정보가 붙은 https는 거부된다.
- 기간, 플랫폼, 빌드 대상 지정.
- 긴급 공지: 최초 표시, 같은 실행에서 재표시 없음, "나중에" 후 다음 실행에 재표시, 확인 후 재표시 없음, 수정된 revision은 재표시.
- 일반·중요 공지는 팝업 없음.
- 빈 피드로 회수(오프라인 다음 실행에서도 유지).
- 오프라인, 손상 JSON, 목록이 아닌 응답, 과대 응답에서도 정상 캐시를 보존한다.
- 디스크의 캐시·상태 파일이 손상돼도 시작한다.
- 7일 넘은 캐시는 목록에만 나온다.
- 네트워크가 멈춰 있어도 `start`는 2초 안에 끝난다. 겹친 갱신 4건이 요청 1건으로 합쳐지고, 간격 제한이 지켜진다.
- 설정이 없는 빌드는 조용히 꺼진다.
- 상태 파일: 동시 읽음 20건이 모두 저장된다. rename 거부 2회 후 재시도로 성공한다. 계속 거부되면 확인 기록을 보존하고 임시 파일을 남기지 않는다.

UI 테스트가 확인한 항목:
- 공지가 여러 개여도 배너는 하나이고 팝업은 뜨지 않는다.
- 긴급 팝업의 확인과 나중에 동작.
- 다른 화면이 위에 있는 동안 도착한 긴급 공지는 띄우지 않고, 홈으로 돌아오면 띄운다.
- 목록에 읽은 공지가 남는다. 긴 본문은 스크롤된다. 허용된 링크에만 버튼이 생긴다.
- 화면 배치: 320px(en 1.5배, ko 2.0배), 휴대폰 가로 740×360(ko 1.3배), 960px 데스크톱에서 팝업, 배너, 목록, 상세가 넘치지 않고 확인 버튼에 닿을 수 있다.
- 실제 `SongsScreen`에 배너가 나오고 기존 안내도 함께 동작한다.

## 5. 운영자 게시 가이드 (Supabase 대시보드)

> 먼저 `005_app_announcements.sql`을 **스테이징**에서 적용하고 확인한 뒤 운영에 적용한다. 이번 작업에서는 어디에도 적용하지 않았다.

1. **초안 작성:** Table editor › `app_announcements` › Insert row.
   - `id`(예: `outage-2026-11-05`), `kind`, 한국어·영어 제목과 본문을 채운다.
   - `published`는 **false 그대로** 둔다.
   - 기간(`starts_at`, `ends_at`)은 UTC로 입력한다(KST − 9시간).
   - 필요하면 `platforms`, `min_build`/`max_build`, 버튼(라벨 두 개와 URL)을 넣는다.
2. **미리 확인:** 초안은 앱에서 보이지 않는다. 확인 방법은 둘이다.
   - 내부 확인용 빌드 번호(예: 9000, 출시하지 않는 번호)를 정해 `min_build = max_build = 9000`으로 게시하고, 내부 빌드를 `flutter build … --build-number=9000`으로 만들어 그 기기에서만 확인한다.
   - SQL editor에서 앱이 보는 결과만 점검한다:
     `set role anon; select id, revision, kind, title_ko from app_announcements; reset role;`
3. **게시:** `published = true`로 바꾸고, 대상 빌드 범위를 실제 값으로 넓힌다(제한이 없으면 빈 값).
   - 앱은 다음 실행 때, 또는 앱이 다시 활성화될 때(15분 간격) 받는다.
   - 긴급 공지는 홈이 안전할 때 한 번 뜬다.
4. **수정:** 오탈자만 고쳐도 내용이 바뀌면 revision이 자동으로 올라 **새 공지로 다시 알린다**(긴급이면 다시 팝업). 다시 알리고 싶지 않은 사소한 수정이라도 현재 계약에서는 다시 알림이 간다. 문구를 신중히 확정한 뒤 게시하라. 기간, 대상, 게시 여부만 바꾸면 다시 알리지 않는다.
5. **회수:** `published = false` 또는 `ends_at`을 지금 시각으로 바꾼다. 앱은 다음 갱신 때 배너, 팝업, 목록에서 지운다. 이미 지난 `ends_at`은 오프라인 기기에서도 바로 숨겨진다.
6. **대상 지정 팁:**
   - 특정 버전의 버그 안내는 `min_build`/`max_build`로 그 빌드에만 보낸다(빌드 번호는 `pubspec.yaml` `version: x.y.z+N`의 N).
   - 데스크톱 전용은 `platforms = {windows,macos}`.
   - 빌드 번호를 모르는 기기(빌드 정보를 읽지 못한 경우)에는 빌드 범위가 없는 공지만 보인다.
7. **한계:**
   - 앱이 아예 실행되지 않거나 홈까지 가지 못하는 장애는 인앱 공지로 전달할 수 없다. 홈페이지 공지, 스토어 설명, 이메일, 푸시가 필요하며 이번 범위 밖이다. 이번에 실제 공지나 메일을 보내지 않았다.
   - Supabase 자체가 장애면 새 공지를 받지 못한다(마지막 캐시만 보인다).
   - 사용자에게 전달되는 시점은 실행이나 재활성화 때이므로 즉시 전달을 보장하지 않는다.

## 6. 확인하지 않은 것 — 완료로 보고하지 않음

- 운영·스테이징 Supabase에 migration 005 적용, 실제 PostgREST 경유 응답(헤더, 정렬, limit, RLS 결과 형식).
- 실제 휴대폰(Android/iOS)과 Mac 화면, 시스템 큰 글꼴, 실제 링크 열기(메일 앱, 브라우저).
- 실제 장시간 오프라인, 앱 업데이트 후 빌드 번호 대상 지정.
- Electron Studio 연동(형식만 문서화, 소스 미변경).
- 운영자 권한 분리(대시보드 접근 권한 관리)와 게시 승인 절차는 운영 정책으로 따로 정해야 한다.
- 공지 문구가 바뀌면 사소한 수정도 다시 알림이 가는 정책을 유지할지(예: "조용한 수정" 플래그)는 후속 결정이다.

## 7. Codex 독립 검증 및 develop 반영 준비 (2026-10-31)

최신 결과는 `develop-verification-2026-10-31.md`를 참조한다.
잘못된 선택적 링크 자료형으로 정상 공지 처리까지 실패하던 문제와,

# Codex 중간 리뷰 — 2026-10-30 클라우드 서버

작성 시점: 서버를 구현하는 도중의 스냅샷이며 최종 결과 판정이 아니다. 현재 소스는 기능 플래그 기본 false를 유지하고 있다.

## 보완 필요: 기존 백업을 PUT 발급 경로에서도 보호

현재 backend/app/routes/storage.py의 presign은 클라이언트 project_id/file_name으로 기존과 동일한 R2 key에 PUT URL을 발급한다. size_bytes도 선택 사항이다. cloud_quota.py가 설명하는 '새 객체를 올리고 RPC로 포인터만 전환'만으로는 기존 사본 불변성이 확보되지 않는다.

- 본인 프로젝트의 현재 meta.key와 같은 key에 새 PUT을 요청하면 DB RPC 이전에 정상 백업을 덮어쓸 수 있다.
- 새 key를 서버에서 만들더라도 발급된 PUT URL을 커밋 후 다시 사용하면 같은 key의 bytes를 바꿀 수 있는지 확인해야 한다. 앱의 UUID만 믿지 말고 실제 객체 저장소의 보장으로 보호해야 한다.
- 계약1 업로드에서 크기가 빠진 요청으로 size 제한/용량 사전 검사를 우회하지 못하도록 한다. 예전 클라이언트 호환이 필요하다면 별도 명시된 제한을 두고 구형 경로로 현재 백업 key를 변경할 수 없어야 한다.
- 다른 곡 ID들이 정규화/120자 절단으로 같은 prefix가 되는 경우에도 기존 백업 삭제/덮어쓰기가 없도록 확인한다.

수용 검증:
1. 현재 유효한 백업 key로 다시 업로드 발급 요청 → 거절하거나 기존 파일을 절대 바꾸지 않는 별도 새 key 발급.
2. 이미 커밋한 객체의 발급 PUT URL 재사용 → 기존에 커밋된 백업 내용이 변하지 않는다.
3. 크기 누락/초과/동시 요청·업로드 취소/409 충돌 → 기존 정상 사본 보존, 쿼터 및 잔여 객체 처리 명확.

운영 R2에서 검증하지 않은 저장소 기능은 지원된다고 단정하지 말고, 구현 계약/테스트 대역/실제 저장소 미확인을 구분해 문서화한다. 기존 요청대로 배포·운영 DB 변경·고객 파일 업로드는 하지 않는다.

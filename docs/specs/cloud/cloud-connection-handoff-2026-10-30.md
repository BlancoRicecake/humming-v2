3. 특히 기존 good backup을 보존하도록 업로드 도중 실패/취소/초과 시 덮어쓰기와 삭제가 안전한지 확인한다. 동시 업로드, 충돌 확인과 메타 갱신의 원자성, 용량 측정 경합을 검증한다. 순서대로 mock만 호출하는 테스트로 원자성을 입증했다고 하지 않는다.
4. 신규 .humtrack 백업을 재사용할지 기존 JSON+오디오 API에 매핑할지 정하고 문서화한다. 서버가 구버전·기능 비활성일 때 앱은 안전하게 중단해야 한다. 계정 토큰은 자체 API에만 보내고 presigned R2 요청에 전파하지 않는다. 서명 URL/토큰/곡 내용을 로그로 남기지 않는다.
5. 앱에 곡별 백업·클라우드 목록·새 기기 복원·클라우드 사본 삭제·사용량을 연결한다. 복원 기본은 새 로컬 곡으로 저장해 기존 작업을 보존한다. 충돌은 기기 유지/클라우드 받기/둘 다 보관을 명확히 처리한다. 삭제는 범위와 확인을 제공한다.
6. 보컬 포함 여부를 사용자가 고른 뒤 업로드한다. MIDI만 백업할 때 오디오 제외가 명확히 표시되어야 한다. 옵트인 해제 시 기존 사본 처리도 설명하고 확인한다. 단순 앱 실행/로그인/설정 표시만으로 업로드하지 않는다.
7. 내부 기능 플래그 기본 꺼짐을 유지해 테스트 계정 및 fixture로 검증할 수 있게 한다. analyze·의미 있는 서버 테스트·Flutter 관련/전체 테스트를 실행한다. 실제 운영 테스트·휴대폰/다른 기기 왕복·실제 소리 판단은 미확인으로 분리한다.

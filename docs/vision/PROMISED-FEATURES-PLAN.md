# 약속했던 Pro 기능 구현 계획 — 클라우드 동기화 · 보컬 보관 · 우선 분석

작성일: 2026-10-13 · 결정 (Heo): 정정 안내로 끝내지 않고 **실제로 만드는 계획부터 세운다.**
근거 조사: 이 문서 작성 시점의 `main` (1.0.13+43) 코드 정적 확인. 실행·운영 설정 확인은 하지 않았다.

## 0. 원칙

- **나오기 전에는 약속하지 않는다.** 앱 안내·약관·스토어 설명은 "현재 제공 기능" 기준을 유지하고, 기능이 출시되는 날 Pro 혜택에 다시 넣는다.
- 클라우드에 보컬을 저장하는 순간 개인정보처리방침의 "작업물은 기기에만 저장, 분석 오디오는 즉시 폐기"가 바뀐다. **방침 개정 + 30일 사전 고지**가 출시 일정의 선행 조건이다.
- 비전과 연결: 클라우드는 데스크톱(여러 기기에서 같은 곡)과 장기 목표인 "함께 노는 공간"(씨앗 공유)의 기반이다.

### 바로 확인해야 할 위험

- **서버에 Pro 확인이 없다.** `storage.py`의 주석대로 "Pro 분기는 UI가 처리". 운영 서버에 R2 설정이 들어가 있다면, 로그인만 한 무료 사용자도 API로 직접 5GB까지 올릴 수 있다 (저장 비용·악용). 감사 문서 B7("서버측 용량 실측·Pro 게이트")이 미해결 상태.
  → 확인: Fly 시크릿에 `R2_*`가 설정돼 있는지, Supabase에 `cloud_projects` 테이블이 있는지.
- 용량(`size_bytes`)을 앱이 보낸 값으로 믿는다. 서버가 R2 실제 크기를 재야 한다.

## 2. 기능별 설계 방향

### 2-1. 클라우드 백업 → 동기화 (1순위)

이미 있는 문구가 설계를 말해 준다: 곡 단위로 **올리기 / 최신화 / 내 기기에 받기 / 클라우드에서만 삭제**.

- **MVP = 곡 단위 수동 백업·복원 (Pro).** 곡 메뉴에서 올리기·받기, 계정 화면에 사용량, 새 기기에서 "클라우드에서 가져오기".
- 데이터: 곡 JSON(SongSpec/저장 포맷)은 `/projects` meta에, 보컬·샘플 오디오는 presigned PUT으로 R2에 직접.
- 충돌: 서버가 이미 `expected_updated_at` 비교 후 409를 준다. 앱은 "기기 버전 유지 / 클라우드 버전 받기 / 둘 다 보관(복제)" 세 가지 선택만 제공.
- 다음 단계(MVP 이후): 자동 동기화(앱 열 때·저장 때), 모바일↔데스크톱 이어 하기.
- 비용 감: R2 $0.015/GB·월, 송신 무료. Pro 한 명이 5GB를 다 써도 약 $0.075/월 (월 구독료 $3.49 대비 2%).

### 2-2. 보컬 보관

- 2-1의 R2 업로드에 보컬 원본을 포함하는 것으로 해결. 따로 만들지 않는다.
- 사용자가 **켜야** 올라가게(옵트인) 하고, 끄면 클라우드 사본 삭제. "영구"라는 표현 대신 "직접 지우기 전까지 보관 (구독 종료 후 n일 유예)"처럼 정확히 쓴다.

### 2-3. 우선 분석 (결정: 만든다)

- 서버의 무거운 분석·렌더 엔드포인트 앞에 **동시 처리 제한 + 우선순위 대기열**을 둔다. 처리 슬롯 일부는 Pro 전용으로 비워 두고, 대기열에서는 Pro 요청이 먼저 나간다. 무료 요청이 굶지 않도록 대기 시간 상한을 둔다.
- Pro 판단은 클라우드와 같은 서버측 권한 확인을 재사용한다. 앱이 보낸 값은 믿지 않는다.
- **정직한 표현**: "서버가 붐빌 때 Pro 요청을 먼저 처리"로 쓴다. 한가할 때는 누구나 즉시 처리되므로 "항상 더 빠름"이라고 약속하지 않는다.
- 측정: 요청별 대기 시간과 등급(Pro/무료)을 로그·Sentry 지표로 남겨, 붐빌 때 실제로 차이가 나는지 확인한다.
- 남은 고민: 허밍 분석을 나중에 폰에서 돌리게 되면(`docs/knowledge/insights.md` 14) 이 혜택의 대상은 서버에 남는 작업(고품질 재분석, 렌더 등)으로 옮겨 간다.

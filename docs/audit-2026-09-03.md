## 4.5 ⚠️ 결정 필요 — 약관·마케팅이 없는 기능을 약속하고 있음

**클라우드 동기화/백업은 앱에 구현돼 있지 않다** (계정 시트에서 주석 처리, `docs/LOOPTAP_TODO.md` #1). 그런데 다음이 이를 Pro 혜택으로 명시한다:

| 위치 | 문구 |
|---|---|
| `docs/legal/terms-of-service.md:44,150` · `landing/terms/index.html:283` | "HumTrack Pro: … **5 GB 클라우드 동기화**(Cloudflare R2 + Supabase), 보컬 영구 클라우드 보관, 우선 분석" |
| `docs/legal/privacy-policy.md:15,38` · `landing/privacy/index.html:413~478` | "Pro 사용자의 보컬·작업물이 R2 에 저장·영구 보관" (실제로는 업로드 자체가 없음) |
| `landing/refund/index.html:231,244,257` | 환불 제한/보상 조건이 "클라우드 동기화" 사용을 전제 |
| `landing/index.html` 가격표·FAQ | ✅ 2026-09-03 수정 — 실제 혜택(무제한 곡 저장 · WAV/MIDI/스템 내보내기)으로 교체 |
| 앱 paywall·계정 시트 | ✅ 수정 (M10) |

랜딩 마케팅 문구는 사실에 맞게 고쳤지만 **약관·개인정보처리방침·환불정책은 법적 문서라 임의로 고치지 않았다.** 둘 중 하나가 필요하다:
1. **클라우드 동기화를 구현한다** — 백엔드 `/projects` · `/storage/presign` 은 이미 살아있고, 남은 건 LoopTap 곡 모델 매핑 + 업로드/복원 UI. (이 경우 백엔드 B7 = 서버측 용량 실측·Pro 게이트도 함께 해야 함.)
2. **약관을 개정한다** — Pro 정의에서 클라우드 항목 제거, 개인정보처리방침의 R2 보컬 보관 항목을 "미사용"으로 정정, 환불정책의 클라우드 관련 조건 삭제. 개정 시 기존 구독자 고지(앱 내 공지 + 시행일)가 필요하다.

권장: **2번을 먼저** (지금 이 순간에도 사실과 다른 상태) 하고, 클라우드 동기화는 별도 기능으로 로드맵에 올린다.

## 4.6 ⚠️ 학습 피치 보정 모델은 기본 OFF 로 두었다 (2026-09-04 측정 결과)

B9(`models/` 를 이미지에 포함) 을 그대로 배포하면 **사용자 멜로디가 바뀐다**. 출시 이후 지금까지 프로덕션은 모델 없이(휴리스틱으로) 돌아왔고, 사용자들은 그 결과에 만족해 결제까지 했다. 5개 레퍼런스 샘플로 모델 유/무를 A/B 한 결과:

| 지표 | 모델 없음(현 프로덕션) | 모델 있음 |
|---|---|---|
| 멜로딕 노트 중 음정 변경 | — | **41/78 (53%)** — +1반음 40, −1반음 1 |
| `pitch − pitch_raw` 평균 | −0.05 반음 | **+0.45 반음** (5개 샘플 전부 샤프 방향) |
| 부른 음에서 0.5반음 이상 벗어난 노트 | 10% | **45%** |

노트 개수·시작/끝·키 감지·퍼커션 분기는 **완전히 동일**하다. 바뀌는 건 음높이뿐.

원인의 최소 일부는 **중첩 적용**이다: `apply_learned_pitch_correction` 이 Pitch Assistant 가 이미 스냅한 `note.pitch` 에 다시 ±1반음을 더해(`analyze.py`), 한 노트가 측정값에서 ~1.4반음까지 벌어진다. 모듈 docstring 은 "small conservative … 'no correction' 이 기본" 이라고 적혀 있으나 실제 동작은 그렇지 않다 → 모델 자체 결함 가능성.

**조치**: `AnalyzeOptions.learned_pitch_correction` 기본값을 `True` → `False`. 모델 파일은 이미지에 포함하되(드럼 분류기는 개선 확인 — 21개 중 1개를 더 정확하게 재분류), 피치 보정은 재학습·재검증 전까지 opt-in. 기존 사용자 결과는 그대로 유지된다.

**후속**: 중첩 적용을 없애고(`pitch_raw` 기준으로 적용) HumTrans 정답셋으로 재평가 → 그때 기본 ON 여부 재결정. `backend/tests/test_learned_models.py` 가 기본값을 고정한다.

## 5. 배포 시 필요한 수동 작업 (코드 밖)
1. **Supabase 마이그레이션** `backend/migrations/002_iap_transaction_binding.sql` 적용.
2. **Fly secrets 확인**: `SUPABASE_JWT_SECRET`(또는 JWKS 사용 시 asymmetric 키 프로젝트인지), `IAP_WEBHOOK_SECRET` 또는 `GOOGLE_PUBSUB_AUDIENCE`, `APPLE_BUNDLE_ID`, `GOOGLE_PACKAGE_NAME`. `fly secrets list`로 점검.
3. **Apple App Store Server Notifications V2** URL이 `https://api.hum-track.com/iap/webhook/apple`로 등록돼 있는지, Google RTDN Pub/Sub push가 `?token=<IAP_WEBHOOK_SECRET>` 를 포함하는지.
4. 앱 업데이트 배포 후 기존 구독자는 첫 실행의 restore→verify로 거래 ID가 백필됨. 그 전까지는 웹훅이 해당 유저를 못 찾음(로그 `no_user`). 이 구간은 `backend/tools/reconcile_subscriptions.py` 로 메운다 (infra/SETUP.md §10).
5. **배포 순서**: 마이그레이션 → 백엔드 → 앱. 순서가 바뀌어도 결제가 죽지는 않도록 백엔드가 002 컬럼 부재를 감지해 구 스키마로 저장하지만(로그 ERROR), 그 동안 웹훅 매핑은 동작하지 않는다.
6. 배포 후 확인: `curl -fsS https://api.hum-track.com/health`, Fly 로그에 `learned model ...: loaded` 3줄, Sentry environment 가 `production` 으로 찍히는지, 그리고 Sandbox 계정으로 구매 → `/iap/status` 가 `pro:true` → 해지 후 웹훅 수신 → `expired` 전이.

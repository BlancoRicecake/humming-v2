# 클라우드 출시 차단 항목 작업지시서

기준: `RELEASE-CHECKLIST-2026-10-31.md` C1~C4/P1.
원래 구현 범위와 수용 기준을 보존한 지시서다. 아래 범위 중 지속 큐·임대·탈퇴·주기적
작업과 계약 검증기는 로컬 구현·검증을 마쳤다. **실제 서비스 적용·검증은 미완료**다.
최신 결과와 적용 순서는 [CLOUD-LIFECYCLE-2026-10-31.md](CLOUD-LIFECYCLE-2026-10-31.md)를 따른다.
기존 미커밋 파일이 최신이고,
프로젝트 작업은 `C:/src/humming-v2` 안에서만 한다. 운영 데이터/키/플래그/정책을
직접 바꾸거나 고객 공지·이메일을 보내지 않는다.

## 1. 반드시 보존할 계약

- 클라우드 사본은 검증된 `.humtrack` 1개. 복원은 새 로컬 곡이다.
- 업로드만 Pro, 구독 만료 뒤 기존 사본의 목록/복원/삭제는 허용.
- `X-Expected-User`, 계정별 링크, 크기·해시·서명 헤더 검증, create-only up 키,
  외부에 PUT URL이 나가지 않는 bk 키, DB CAS/충돌 동작을 보존.
- C1~C6 독립 회귀와 서버/앱 전체 검증을 약하게 만들지 않는다.
- `CLOUD_BACKUP_WRITES_ENABLED=false` 긴급 모드는 새 쓰기를 막고 읽기/삭제를 유지.
- 현재 참조된 사본과 사용자 기기 파일을 스윕하지 않는다. 버킷 전체 수명 만료 규칙을
  추가하지 않는다. R2 정책 `infra/cloudflare/r2-lifecycle.md`를 존중한다.

## 2. 지속되는 삭제 작업과 주기적 정리

현재 `routes/projects.py`의 `_cleanup_after_commit`/`_stale_objects`와
`routes/account.py`의 best-effort 삭제를 읽고 설계한다.

필수 동작:

1. 삭제/정리할 **정확한 키 집합**과 소유 계정·이유·시도 수·다음 재시도 시각을
   영속화한다. 큐와 계정 삭제 차단 표시는 Auth 사용자 cascade로 사라지면 안 된다.
   필요한 다음 번호 migration을 추가하되 운영에는 적용하지 않는다.
2. 진행 중 업로드/커밋을 식별하는 유한한 임대/기한 또는 동등한 원자적 보호를 둔다.
   “24시간 지났으니 안전”이라는 가정만으로 아주 늦게 끝나는 커밋을 삭제하지 않는다.
   GC가 결정한 키를 뒤늦은 커밋이 정상 참조로 만들 수 없어야 한다.
3. 스윕 시점의 DB 참조와 진행 중 임대를 다시 확인한다. 다른 기기가 교체한 새 bk는
   남기고 이전 사본·만료된 up·결과 불명 사본만 정리한다. 알 수 없는 형식/수정 시각은
   보수적으로 남기고 관측 가능하게 한다.
4. R2 `delete_objects` 응답의 개별 `Errors`까지 확인한다. 부분 실패는 완료 처리하지 않고
   정확한 실패 키만 bounded backoff로 재시도한다. 프로세스 재시작 후에도 이어진다.
5. 작업 한 번의 계정/객체 수·동시성·실행 시간을 제한하고 dry-run을 기본으로 제공한다.
   운영자 전용 CLI/작업으로 실행하고 공개 익명 파괴 API를 만들지 않는다.
6. 프로젝트에 다음 업로드가 없어도 정리가 실행되어야 한다. 실제 배포/예약 연결은
   계획·실행·확인 상태를 구분해 보고한다.
7. 삭제 후 사용량은 실제 남은 객체로 재측정한다. 업로드/교체가 동시에 진행될 때
   한도 초과나 사용량 누락을 재현하고 처리 규칙을 확인한다.

## 3. 계정 탈퇴

- 먼저 영속적인 탈퇴/삭제 작업과 새 쓰기 차단을 확정한 뒤 Auth 삭제를 수행한다.
- R2 실패나 Supabase 응답 유실 뒤에도 작업을 찾고 재시도할 수 있어야 한다.
- 이미 발급된 presigned PUT은 Auth 계정 삭제와 함께 즉시 무효화되지 않는다.
  최대 URL TTL+여유 시간 뒤 재스윕/검증하여 늦게 도착한 업로드도 제거한다.
- 재시도는 멱등적이어야 한다. 삭제 진행/완료를 구분하고 지키지 못한 완료를 안내하지 않는다.
- 구독은 스토어에서 직접 관리한다는 기존 안내와 로컬 작업물 보존을 유지한다.

## 4. 실제 서비스 검증을 다시 만들기

`backend/tests/test_cloud_sync.py` 11개는 pre-contract-1이라 무조건 skip이다.
이를 활성화만 하지 말고 현재 계약용 opt-in 검증기를 새로 만든다.

- 명시적 테스트 계정 2개, 새 고유 project ID/객체만 사용. 고객 키·prefix 조회/삭제 금지.
- 실제 Supabase Auth/PostgREST/RLS/RPC와 R2를 통과해야 한다. 대역과 분리 보고한다.
- 조건부 PUT·크기/해시·CopyObject·URL 재사용·응답 유실·삭제 오류·CAS 충돌·계정 전환,
  구독 만료 read/delete, 용량 초과·중단·재시도·정리와 탈퇴를 확인한다.
- 실행 전 대상 URL과 테스트 소유권 확인, dry-run 목록을 먼저 만든다.
  자격 증명은 환경/제외 파일로만 받고 토큰·서명 URL·음원·곡 제목을 로그에 남기지 않는다.
- 새 검증기와 앱/서버 수정은 로컬 PG+FakeR2 → 격리 실제 서비스 → 폰/Windows 실제 왕복
  순서로 확인한다. 실제 접속이 없으면 실서비스 검증 완료로 보고하지 않는다.

## 5. 고지 문구와 스토어 제출을 위한 사실표

현재 개인정보/약관은 아래 내용을 반영하지 못한다. 활성 문서를 몰래 바꾸거나
시행일을 확정하지 말고 KO/EN 개정안·적용 위치·고지/확인 기록을 별도로 준비한다.

- 자동 동기화가 아닌 사용자가 누르는 Pro 수동 백업.
- 노트만/녹음 포함의 차이, 녹음 포함은 기본 꺼짐의 명시적 선택.
- R2 객체와 Supabase 메타데이터의 실제 저장 위치/수탁자·접근·삭제 경로.
- 서버 기본 한도는 5GiB지만 운영 override를 확인하기 전 고객 보장량으로 쓰지 않는다.
- 구독 만료 후 기존 사본 읽기/복원/삭제와 신규 업로드 제한.
- 클라우드 사본 삭제와 로컬 원본 보존, 탈퇴 작업의 지연/완료 기준.
- 미참조 임시 파일 정리와 보관 중인 정상 사본 삭제 정책을 구분.
- 웹 정책/앱 내 KO·EN/스토어 데이터 공개/App Privacy·Data Safety/앱 안내를 맞춘다.
- 기존 문서가 정한 개정 고지 절차와 실제 이력을 확인하고 시행일을 정한다.
  Firebase 초안의 2026-11-01을 클라우드에 그대로 재사용하지 않는다.

## 6. 수용 기준과 보고

새 SQL/서버 회귀: GC 중 다른 기기 커밋, 응답 유실, R2 부분 실패, 재시작, 큐 경쟁,
오래 멈춘 커밋, 탈퇴 후 지연 PUT, 다른 계정 격리, 참조 사본 보존을 확인한다.
스윕 전후 참조 키·객체 바이트·실제 사용량·재시도 이력을 증거로 남긴다.

작업 완료 보고에는 바뀐 파일/마이그레이션, 각 테스트 결과, 미확인 실서비스/기기,
운영 적용 순서·긴급 중단·복구 방법을 포함한다. 기존 라이브 테스트의 skip을 숨기지 않는다.
